## Threat model
A **Threat model** is a structured representation of all the information that affects the security of an application.
A threat model typically includes:

- Description of the subject to be modeled
- Assumptions that can be checked or challenged in the future as the threat landscape changes
- Potential threats to the system
- Actions that can be taken to mitigate each threat
- A way of validating the model and threats, and verification of success of actions taken

*Ref:* https://en.wikipedia.org/wiki/Threat_model

## Open Threat Model (OTM)
The [Open Threat Model](https://github.com/iriusrisk/OpenThreatModel) is a standardised representation of Threat Model that is platform independent and can be applied to any system or component (even non-IT systems).

## Trust boundary
A **trust boundary** is any point where the level of trust or control changes between systems, stack components, applications, or users. These boundaries exist between:

- Stack components (e.g., OS and Runtime, or CPU and Firmware...)
- Networks (e.g., Public, private...)
- Connections (e.g., 3rd party, trusted partners...)
- Service providers (e.g., in-house, cloud-hosted...)

**N.B.:** In the Open Threat Model, the Trust Boundary is the edge of a **Trust Zone.**
**N.B:** In IETF's [RATS specification](https://datatracker.ietf.org/doc/rfc9334/), Trust Boundaries can be assimilated as "Layers" for the purposes of Layered Attestation.

## Remote ATtestation procedureS (RATS)
We will refer to [IETF's RATS](https://datatracker.ietf.org/doc/rfc9334/) as the model architecture and lexicon's source for the attestation and appraisal services. The RATS specification: 
> "provides an architectural overview of the entities involved that make such tests possible through the process of generating, conveying, and evaluating evidentiary Claims. It provides a model that is neutral toward processor architectures, the content of Claims, and protocols."

## Attester
In Remote ATtestation procedureS (RATS), one peer (the **"Attester"**) produces believable information about itself (**"Evidence"**) to enable a remote peer (the **"Relying Party"**) to decide whether or not to consider that Attester a trustworthy peer.

## Verifier
The Verifier appraises **Evidence** via appraisal policies and creates the **Attestation Results** to support Relying Parties in their decision process.

## Reference Value Provider
A role performed by an entity whose **Reference Values** help Verifiers appraise Evidence to determine if acceptable known Claims have been recorded by the Attester.

## Evidence
A set of Claims generated by an Attester to be appraised by a Verifier.  Evidence may include configuration data, measurements, telemetry, or inferences.

## Reference Values
A set of values against which values of Claims can be compared as part of applying an Appraisal Policy for Evidence. Reference Values are sometimes referred to in other documents as "known-good values", "golden measurements", or "nominal values". Reference Values might be general and be used in any sort of comparison other than just equality.

## Attestation Service
A mechanism that provides cryptographic proof that a computing environment, such as a Trusted Execution Environment (TEE), is running trusted software and has not been tampered with.
Depending on the Trust Boundary, it attests the integrity and authenticity of the environment by taking "measurements" generated before execution (i.e.: a CPU unique ID, a hash of the firmware's code...).
In our framework the attestation might therefore vary, as it is dependent on the Trust Boundary and the measurements involved.

When a third party is involved, the attestation service is mediated through a trusted intermediary (e.g., Intel's Attestation Service for SGX or AMD's SEV attestation server).

## Entity Attestation Token (EAT)
IETF specification [EAT](https://datatracker.ietf.org/doc/draft-ietf-rats-eat/) that standardises the token providing an attested claims set describing state and characteristics of an entity (e.g., a device like a smartphone, IoT device, network equipment or such).  This claims set is used by a relying party, server or service to determine the type and degree of trust placed in the entity.
